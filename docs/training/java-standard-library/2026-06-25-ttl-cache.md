## 成果物

### CacheEntry

```java
import java.time.Instant;

record CacheEntry<T>(T value, Instant expiresAt) {
    boolean isExpired(Instant now) {
        return !expiresAt.isAfter(now);
    }
}
```

### TTL Cache

```java
import java.time.Duration;
import java.time.Instant;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;

class TtlCache<K, V> {
    private final ConcurrentHashMap<K, CacheEntry<V>> store = new ConcurrentHashMap<>();
    private final Duration ttl;

    TtlCache(Duration ttl) {
        this.ttl = ttl;
    }

    Optional<V> get(K key) {
        CacheEntry<V> entry = store.get(key);
        if (entry == null) {
            return Optional.empty();
        }
        if (entry.isExpired(Instant.now())) {
            store.remove(key);
            return Optional.empty();
        }
        return Optional.of(entry.value());
    }

    void put(K key, V value) {
        store.put(key, new CacheEntry<>(value, Instant.now().plus(ttl)));
    }

    void evict(K key) {
        store.remove(key);
    }
}
```

### Repositoryの前にCacheを挟む

```java
class CachedExpenseReader {
    private final ExpenseRepository repository;
    private final TtlCache<Long, Expense> cache;

    CachedExpenseReader(ExpenseRepository repository, TtlCache<Long, Expense> cache) {
        this.repository = repository;
        this.cache = cache;
    }

    Expense getExpense(long id) {
        return cache.get(id).orElseGet(() -> {
            Expense expense = repository.findById(id)
                    .orElseThrow(() -> new IllegalArgumentException("経費申請が見つかりません"));
            cache.put(id, expense);
            return expense;
        });
    }

    void evict(long id) {
        cache.evict(id);
    }
}
```

## 実務への接続

キャッシュは読み取り性能を上げる一方で、更新後に古いデータを返すリスクがある。`expenses` では承認、却下、提出後に対象IDのキャッシュを削除する必要がある。さらにトランザクション中に削除するのか、コミット後に削除するのかで整合性が変わる。

## リファクタ観点

- キャッシュ対象は本当に更新頻度が低く、読み取り頻度が高いか確認する
- 更新失敗時にキャッシュだけ消えないよう、削除タイミングを整理する
- `null` 結果をキャッシュする必要があるか検討する
- キャッシュのキー設計を明確にする
- DTOとドメインオブジェクトのどちらをキャッシュするか決める

### 作業所感

キャッシュは実装自体よりも、いつ無効化するかの判断が難しいと感じた。特にDB更新とキャッシュ削除の順序がずれると、古いデータを再キャッシュする可能性がある。`expenses` の `transactionAware()` はその問題を避けるための重要な設定であり、リファクタ時にもキャッシュ整合性を崩さないよう注意が必要だと分かった。
