## 成果物

## リファクタ方針

大きな設計変更を一度に行わず、テストで振る舞いを固定してから責務を分ける。

1. 現状の振る舞いを守るテストを追加する
2. 命名ゆれ、コメント誤字、明確なバグ候補を先に直す
3. Serviceの状態遷移処理を小さく整理する
4. 通知処理をメッセージ生成、保存、配信へ分ける
5. Export処理をFormatter、Strategy、Controller責務へ分ける
6. MyBatis XMLの重複条件を整理する
7. Observabilityのログ、メトリクス、traceIdを見直す

## 作業候補

### 1. テスト追加

- `ExpenseService#submit`、`approve`、`reject` の正常系、異常系を追加する
- 状態遷移の単体テストをDBなしで書けるようにする
- CSVエスケープ処理のテストを追加する
- 通知メッセージ生成のテストを追加する

### 2. 命名と明確な修正

- `PendignNotificationMapper.xml` のファイル名を `PendingNotificationMapper.xml` に修正する
- WebSocket Subscriberでdestinationをnullにした後に参照している箇所を確認する
- Content-Typeのtypoやログプレースホルダーの崩れを確認する
- コメントの誤字を修正し、長すぎる説明は要点に圧縮する

### 3. `ExpenseService` の整理

- 存在チェック、状態チェック、versionチェックの重複を整理する
- 状態遷移の判断をドメインオブジェクトへ寄せる
- audit log作成処理を専用メソッドまたは専用サービスへ切り出す
- イベント発行処理を状態変更後の明確なステップとして整理する

### 4. 通知処理の整理

- `ExpenseKafkaNotificationConsumer` から通知メッセージ生成を切り出す
- 未読通知保存、メール通知、WebSocket配信を処理単位で分ける
- Retry/DLTログに必要な情報を整理する
- 同じイベントを再処理しても二重登録にならないか確認する

### 5. Export処理の整理

- CSV行生成をFormatterへ切り出す
- Excel、PDF、CSVの共通処理と固有処理を分ける
- ControllerはHTTPヘッダーとレスポンス生成に集中させる
- 大量データ出力時の件数、処理時間、失敗理由をログに残す

### 6. MapperとSQLの整理

- 検索条件の重複を見直す
- `${}` を使う箇所は許可リスト検証とセットで管理する
- 読み取り用、更新用、エクスポート用の責務を分けられるか確認する
- migrationとMapperの命名、カラム名、型の対応を確認する

### 7. Observabilityの整理

- `traceId` がログ、監査ログ、Kafkaメッセージに一貫して渡るか確認する
- Actuator/Prometheusで見るべき指標を整理する
- Kafka Consumer失敗数、通知DLT件数、CSV出力件数などの観測候補を作る
- ログレベルが本番運用で過剰にならないか確認する

## 優先順位

| 優先度 | 作業 | 理由 |
| --- | --- | --- |
| 高 | テスト追加 | 変更前に振る舞いを固定するため |
| 高 | 明確なバグ候補、命名ゆれ修正 | 影響が小さく、保守性がすぐ上がるため |
| 中 | `ExpenseService` の責務整理 | 将来の状態追加や通知追加に備えるため |
| 中 | 通知Consumerの分割 | Kafka、メール、DB、WebSocketが混在しているため |
| 中 | Export処理の分割 | CSV/PDF/Excelの変更を安全にするため |
| 低 | 大きな設計変更 | テスト追加後に段階的に行うべきため |
